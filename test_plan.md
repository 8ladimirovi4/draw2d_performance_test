# План тестирования производительности отображения схем (draw2d)

## Цель

Проверить скорость **полного отображения схемы** в браузере после того, как пользователь (клиент) завершил **HTTP-запрос** за данными документа: от начала обработки ответа до визуально и логически завершённой отрисовки на холсте draw2d.

На текущем этапе тестируется только **клиентская** часть в **Google Chrome** (один тип клиента). Этап с обновлением фигур по сигналам **WSS** от сервера планируется отдельно; настоящий документ закладывает метрики и контур так, чтобы позже можно было добавить сценарии «инкрементального обновления» без смены методологии.

## Входные данные (фикстуры)

- [PER_001](https://wiki.yandex.ru/mt/mt-rd/scada/scada-hld/scada-nfuncreq/qaattr/#PER_001)
- [PER_002](https://wiki.yandex.ru/mt/mt-rd/scada/scada-hld/scada-nfuncreq/qaattr/#PER_002)
- [PER_003](https://wiki.yandex.ru/mt/mt-rd/scada/scada-hld/scada-nfuncreq/qaattr/#PER_003)
- [PER_010](https://wiki.yandex.ru/mt/mt-rd/scada/scada-hld/scada-nfuncreq/qaattr/#per10)
- Примеры компонентов `https://github.com/freegroup/draw2d`
- Документация библиотеки `https://freegroup.github.io/draw2d/index.html#/api/draw2d`
- Инструмент для замера показателей быстродействия:
- `https://w3c.github.io/paint-timing/`
- `https://w3c.github.io/user-timing/`
- Библиотека draw2d загружает модель через **`draw2d.io.json.Reader`**.
- Исходные схемы в формате mxGraph (пример: `buttons.xml, 1x4kПС-1103510.xml`) используются как **эталон сложности**: по ним готовится **`buttons.json и 1x4kПС-1103510.json`** (и при необходимости другие фикстуры), где **число и характер фигур/связей** сопоставимы с XML, чтобы бенчмарк отражал реальную нагрузку, а не упрощённый макет.
- Конвертация XML → JSON — **офлайн**, один раз (или скриптом в репозитории): в рантайме тестов достаточно стабильного JSON в репозитории либо локальной папке фикстур.

## Среда измерений


| Параметр | Значение (этап 1)                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Браузер   | Google Chrome (конкретную версию фиксировать в отчёте прогона)                                                                                                     |
| Клиентов | Один инстанс браузера на прогон сценария                                                                                                                                 |
| Сеть         | Локально: HTTP к статике или простому dev-серверу; при имитации сети — явно документировать throttling (отложенный этап) |

**Общепринятые практики воспроизводимости:**

- Закрыть лишние вкладки и расширения, по возможности использовать чистый профиль или отдельный user-data-dir для серий замеров.
- Фиксировать разрешение окна и масштаб (device pixel ratio).
- Делать **прогрев** (1–2 прогона) и **не включать** их в статистику.
- Для каждой фикстуры: **несколько прогонов** (рекомендуемо 10–30), отчитывать **median**, при необходимости **p75**; отмечать выбросы.

## Метрики

### 1. Web Vitals (браузер)

- **FCP (First Contentful Paint)** — через [Paint Timing API](https://w3c.github.io/paint-timing/) / `PerformanceObserver` (`entryType: 'paint'`, событие с именем, соответствующим первому отображению контента).
- **LCP (Largest Contentful Paint)** — через `PerformanceObserver` (`entryType: 'largest-contentful-paint'`).

**Ограничение:** при доминирующей отрисовке в **canvas** LCP может отражать не «всю схему», а другой крупный элемент страницы. Поэтому LCP и FCP используются как **общие** показатели загрузки страницы и первых отрисовок, но **не как единственный** критерий «схема полностью нарисована».

### 2. Прикладные метрики (обязательно для цели задачи)

Все имена — через [User Timing API](https://w3c.github.io/user-timing/) (`performance.mark` / `measure`), чтобы их было видно в Performance panel и можно было экспортировать в отчёт.


| Метрика                      | Смысл                                                                                                                                         |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `http_fetch_end`                    | Момент завершения получения тела ответа (после`fetch`/XHR), до парсинга JSON и до `unmarshal` |
| `unmarshal_start` / `unmarshal_end` | Обёртка вокруг`draw2d.io.json.Reader.unmarshal` (или эквивалентного пути загрузки модели)          |
| `schema_visible`                    | Момент, когда считается, что схема отображена целиком (см. критерий ниже)               |

**Критерий «схема отображена целиком» (рекомендация):**

- После `unmarshal_end` выполнить **один или два кадра** `requestAnimationFrame` и затем поставить маркер `schema_visible` (так учитывается отложенная отрисовка canvas/SVG).
- Дополнительно (при необходимости жёсткой валидации): проверка, что число дочерних фигур/связей на canvas совпадает с ожидаемым для фикстуры.

**Итоговая задержка от HTTP (главный показатель этапа):**

- `measure('display_after_http', 'http_fetch_end', 'schema_visible')` — время от конца HTTP до «полной» отрисовки по принятому критерию.

### 3. Дополнительно (по мере необходимости)

- Длительность парсинга JSON (`JSON.parse`), если отделена от сети.
- Long tasks (>50 ms) через `PerformanceObserver` (`longtask`), для диагностики блокировок основного потока.

## Архитектура тестовой сборки (этап 1)

1. **Статическая тестовая страница** (например, `perf/index.html` или аналог в корне `perf/`): минимальный layout, контейнер под canvas, подключение собранного `dist/draw2d.js`, без лишнего UI.
2. **Загрузка фикстуры по HTTP** — `fetch('fixtures/buttons.json')` (или параметр `?fixture=buttons`), чтобы цепочка была близка к реальному сценарию «запрос → ответ → отрисовка».
3. **Сбор метрик в странице** — `PerformanceObserver` (buffered: true где поддерживается) + user timing; вывод в консоль или `postMessage` для драйвера.
4. **Дофиксация фикстур** — каталог `perf/fixtures/` с `buttons.json` и манифест (описание: ожидаемое число фигур/рёбер, происхождение от `buttons.xml`).
5. **Скрипт офлайн-конвертации** (опционально в `perf/tools/`) — из `buttons.xml` в JSON draw2d с сохранением масштаба сложности; повторяемый запуск при смене исходного XML.

## Порядок внедрения (пошагово)

1. Создать структуру каталогов `perf/` (страница, `fixtures/`, при необходимости `tools/`).
2. Подготовить `buttons.json` по принципу сопоставимости с `buttons.xml`; задокументировать в манифесте.
3. Реализовать на странице: `fetch` → parse → `unmarshal` → rAF → маркеры и `measure('display_after_http', ...)`.
4. Подключить наблюдателей FCP/LCP и записать в единый объект результата прогона (для последующего экспорта JSON).
5. Локально: серия прогонов в Chrome, таблица median/p75 по каждой метрике и фикстуре.
6. (Опционально) Автоматизация: Playwright/Puppeteer открывает страницу, ждёт сигнал завершения, сохраняет артефакт; в CI — без жёстких порогов на первых порах или с порогами только на регрессию.
